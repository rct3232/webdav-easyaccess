# E2E Coverage Plan

## Purpose

This document is the canonical planning and inventory document for browser-level end-to-end coverage in WebDAV EasyAccess.

Use it to:

- track which user-visible flows should be covered by Playwright
- keep E2E scope aligned with product behavior rather than with the current test suite
- separate true browser flows from scenarios that are better covered by route integration, RTL/MSW, or unit tests
- define rollout order and ownership when expanding the `e2e/` suite

This document does **not** replace feature docs, route specs, or test summaries.

## Relationship to Other Docs

Use the following split consistently:

| `docs/TESTING_STRATEGY.md`                         | Testing principles, layer decisions, mocking policy, and E2E policy rules                                                |

When these documents differ, treat runtime behavior and the most specific contract doc as the source of truth. If a documentation mismatch affects planning, record it here in the notes column instead of silently inventing a new contract.

## Scope

This document covers **browser-observable** flows that a real user can perform through the app UI:

- public auth routes
- protected routing
- file explorer flows
- share-link flows
- MyPage user/admin flows
- desktop-only and mobile-only interaction differences

This document does **not** attempt to fully catalogue:

- every server-side ACL or error matrix
- every API branch that has no meaningful browser entry point
- internal implementation details

Those scenarios should still be tested, but often outside Playwright.

## Ownership Rules

### Platform ownership

- Keep desktop and mobile E2E interactions in separate spec ownership when the interaction surface differs.
- Do not centralize desktop context-menu interactions and mobile action-sheet interactions behind a single conditional-heavy helper.
- Platform-agnostic core flows may live in a shared spec that runs under both desktop and mobile projects, as long as the exercised user path and assertions remain the same across projects.
- Shared helpers may contain only platform-agnostic seams:
  - login/auth setup
  - deterministic resource naming
  - fixture loading
  - stable item locators such as `data-file-path`
  - common explorer entry seams such as opening the FAB menu or an item's shared "More actions" trigger before platform-specific actions diverge

### Selector policy

- Prefer semantic selectors first.
- Use `data-file-path` for concrete explorer items.
- Use `data-testid` only for documented unstable seams such as FAB roots, icon-only action entries, or dialog fields/buttons whose semantic access is not stable enough for E2E.
- For SpeedDial-style menus, prefer visible `menuitem` names when that accessibility surface is stable in the E2E environment.

### Assertion policy

- Verify user-visible outcomes, not implementation details.
- Prefer navigation result, visible UI state, rendered text, disabled/enabled state, dialog presence, and item visibility over internal request inspection.
- Use request inspection only when the interaction itself is the behavior under test and there is no clearer user-visible anchor.
- Assert only inside listings the case owns; a shared/unbounded listing (e.g. the admin root) is not a valid assertion anchor (assertion-context containment — [TESTING_STRATEGY.md](TESTING_STRATEGY.md)).
- Each case removes its owned base folder via the API in `afterEach`, so per-case data never accumulates in shared listings across a run.

### Feature-doc anchors

- Use `docs/features/*.md` for feature-specific E2E guidance that other contributors need at the product boundary, such as:
  - selectors that are intentionally stable for that feature
  - desktop/mobile interaction ownership unique to that feature
  - feature-local testing constraints that would be too vague in the global plan
- Do not duplicate the full inventory table, rollout order, or status tracking inside feature docs.
- If a feature has no such special E2E guidance, it is acceptable for that feature doc to link here without adding a dedicated E2E subsection beyond representative testing anchors.

### Runtime assumptions

- App origin is the local client used by the E2E environment.
- The default and core groups run against S3 (MinIO) storage plus the metadata backend. The WebDAV group adds one shared bytemark instance; no other group starts a WebDAV container.
- The baseline `.env.e2e` setup provides a deterministic admin password.
- The E2E Docker stack is provisioned by the `e2e:server` webServer command before the app server boots: `scripts/e2e-wait-healthy.mjs` runs an idempotent `docker compose -f docker-compose.e2e.yml up -d` and waits for the group's required containers to be healthy. There is no manual `dev:webdav:start` prerequisite.
- `e2e/global-setup.ts` never tears the stack down (that would wipe the Postgres volume out from under the running server). It resets the data state instead: TRUNCATE all app tables (preserving `_schema_migrations`) + re-seed admin and base users with home `file_nodes` roots. It ensures the MinIO platform bucket and empties it once for a deterministic baseline; the WebDAV job resets its one bytemark root. `e2e/global-teardown.ts` empties the bucket and stops the stack (`down -v`).
- **Setup-wizard runtime assumption (hermetic):** the setup specs are fully isolated from the shared E2E state above. The S3 and WebDAV splits each spawn their own scratch server instance on the project's scratch slot (own env file via `DOTENV_CONFIG_PATH`, own sqlite path, own scratch PG DB `webdav_e2e_setup_<project>`) and supervise their own process lifecycle because restart is the behavior under test. The shared `:5002` server and `:3000` client still boot for the run but are unused by the setup projects.

## Execution Groups and Backend Ownership

S3 is the default product backend. Generic functional behavior is verified on
S3. The WebDAV group verifies behavior that is inherently WebDAV-specific, but
migration ownership is direction-aware: it depends on both source and
destination backend. An S3 destination may require a WebDAV source; a generic
gate/role case may use S3 source -> WebDAV destination tarpit in the default
group; real WebDAV source/destination behavior stays in the WebDAV job.

| Group      | Command                   | Backend     | Persistent infrastructure                     | Case set and projects                                                                       | Release role                   |
| ---------- | ------------------------- | ----------- | --------------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------ |
| Default S3 | `npm run test:e2e`        | S3 only     | PG + MinIO + shared API/client                | Full non-WebDAV matrix; includes the core subset. Platform projects plus all S3 scratch.    | Required generic gate          |
| Core       | `npm run test:e2e:core`   | S3 only     | PG + MinIO + shared API/client                | Fast S3 subset: platform core plus registration-settings.                                   | Optional fast pre-merge subset |
| WebDAV     | `npm run test:e2e:webdav` | WebDAV only | PG + MinIO + shared API/client + one bytemark | Platform smoke grep, WebDAV setup/migration/admin-config splits, and WebDAV reconciliation. | Required WebDAV-specific gate  |

Rules:

- Platform cases keep their platform ID family. They are unambiguously S3, and
  the WebDAV smoke deliberately reuses their IDs.
- Backend-specific hermetic cases use backend-qualified IDs (see "ID Migration
  (S3-First Restructure)" below).
- The default group is the full non-WebDAV gate and includes the core cases.
  The core group is a fast subset of the default gate.
- Default and core start no WebDAV container. Only the WebDAV job starts a
  WebDAV container, and that job starts one shared bytemark for the whole run.
- No Playwright project has `dependencies`. Projects are independent siblings;
  the worker count is the only concurrency throttle. Scratch servers are limited
  by the worker count, not by an E2E slot pool, and there is no per-project
  WebDAV container.
- Desktop and mobile projects own separate scratch slots where the suite needs
  independent process state; there is no dependency chain and no shared scratch
  port. Every slot shifts with the checkout's port band.
- Scratch servers are process isolation for boot configuration, global
  settings, the metadata DB, and restart. The project-scoped scratch directory,
  S3 bucket, PG database, and WebDAV subtree isolate blobs only.
- The WebDAV-only case set is `E2E-WEBDAV-SETUP-001..003`,
  `E2E-WEBDAV-MIG-001..006`, `E2E-WEBDAV-ADMINCFG-001..005`, and
  `E2E-WEBDAV-RECON-001`, plus the platform cases selected by the
  `webdav-smoke-desktop` EXP/SHARE/OVERLAY/TRASH/WEBDAV-RECON grep.

### WebDAV coverage trade-off

The current WebDAV job has 41 cases:

- 13 smoke cases: seven shared core-flow cases, one internal-sharing case, one
  public-share case, three trash cases, and one reconciliation case.
- 28 backend-split cases: 6 setup-wizard, 12 migration, and 10 admin-config.

Before the S3-first restructure, the S3 scratch feature suites booted a WebDAV
file backend. After the restructure they boot S3. The WebDAV job therefore no
longer exercises the collections, retrieval, AI, or trash-admin feature suites'
WebDAV blob paths. This is an accepted trade-off: those suites test feature
behavior rather than WebDAV protocol semantics, while the smoke set still covers
generic WebDAV blob operations (upload, preview, rename, move, share, trash,
restore) and the reconciliation case covers the WebDAV-specific integrity path.
Real WebDAV source/destination behavior remains covered by the WebDAV splits.

The historical "164" figure is not a current group count. It was the old
pre-restructure full WebDAV-backend matrix total, where platform/functional
cases were duplicated against WebDAV; it was not a unique-case inventory. It is
not comparable to the current 41-case WebDAV job and must not be reported as a
coverage regression when comparing group totals.

### Audit-follow-up case caveats

- **Migration D-2 settings realism:** seed multiple real application settings
  with distinct values in the source and compare the copied key/value rows in
  the target. The current marker-only seed and key-only comparison are a known
  audit finding; a row count or marker presence is not sufficient.
- **Default-S3 gate/role:** use an S3 source and a raw TCP tarpit as the WebDAV
  destination. The case must prove `202` start, a deliberate second start
  returning `409`, and the admin/user/anonymous role routing without starting a
  WebDAV container. The existing WebDAV gate/role cases keep a real bytemark
  source and a tarpit destination probe.
- **Exactly-once:** gate setup must not retry a non-idempotent start POST. A
  deliberate second POST proves `409`; the server-side job count/state proves one
  job. Do not classify the thrown error as success, and do not retry Flow F's
  start loop. If a transport retry is unavoidable, it needs an idempotency key
  and a server job-count assertion.
- **Retrieval first Enter:** count `POST /api/search` requests, not responses.
  Typing must issue zero requests; one Enter must issue exactly one. Wait for the
  search-ready/orbit state instead of a blind retry loop or a fixed sleep.
- **Timeout and latency:** infrastructure waits (scratch boot, health, job
  polling) are not product latency SLAs. Release runs with no retries and
  fail-on-flaky; a 4+ worker run is capacity validation only.
- **Skip semantics:** required WebDAV/PG/AI weights absent in CI must fail.
  Expected static skip counts are listed above; any additional skip fails the
  release gate.
- **Same-session state:** do not reload to resume a migration dialog or bypass a
  fetch queue. The current WebDAV resume workaround is slated for removal; the
  observable dialog/request state is the assertion.
- **Undo state:** do not re-open a collapsed tree merely to make an undo
  assertion pass. The current collection undo workaround must either assert the
  intended remount/collapse as product-observable state or wait for a product fix.
- **Debug hygiene:** remove spec `console.log` debugging before merging.

## Scenario Classification

Each flow row should use the following dimensions.

### Priority

| Value | Meaning                                              |
| ----- | ---------------------------------------------------- |
| `P0`  | Required for the first meaningful browser safety net |
| `P1`  | Strongly recommended after `P0` is stable            |
| `P2`  | Useful but deferrable or infra-sensitive             |

### Recommended layer

| Value        | Meaning                                           |
| ------------ | ------------------------------------------------- |
| `playwright` | Best verified through full browser E2E            |
| `rtl-msw`    | Better as client integration with mocked API      |
| `supertest`  | Better as server route integration                |
| `unit`       | Better as unit or hook/service-level verification |

### Viewport

| Value     | Meaning                                    |
| --------- | ------------------------------------------ |
| `both`    | Same observable flow on desktop and mobile |
| `desktop` | Desktop-specific surface or behavior       |
| `mobile`  | Mobile-specific surface or behavior        |

### Status

| Value      | Meaning                                                                             |
| ---------- | ----------------------------------------------------------------------------------- |
| `covered`  | Implemented in the current E2E suite                                                |
| `planned`  | Accepted target for future implementation                                           |
| `deferred` | Intentionally postponed                                                             |
| `non-e2e`  | Tracked here but recommended outside Playwright                                     |
| `retired`  | Removed or split; the ID is never reused                                            |
| `folded`   | No separate test; the assertions are covered by the owner named in the Notes column |

Status discipline:

- Keep `covered` reserved for scenarios that already exist in committed Playwright specs.
- Use `planned` for the current expansion wave until the owning spec lands.
- Use `folded` instead of a hidden gap when a separate test is intentionally
  absorbed by another case; the Notes column names the owner (covered-by).

## Rollout Order

Use the following staged order when expanding browser coverage:

1. `P0` auth and protected-route baseline
2. `P0` desktop and mobile explorer CRUD beyond the current smoke tests
3. `P0` bulk move/copy/delete and mobile download restriction
4. `P0` public share success/error flows
5. `P0` internal sharing lifecycle and approved-user `__shared__` access
6. `P0` `__recent__` entry flows plus remaining MyPage user account/sharing coverage
7. `P0` MyPage admin flows
8. `P1` advanced desktop/mobile interactions, including MyPage mobile drawer coverage
9. `P2` infra-sensitive gestures, denied/no-op drag-and-drop smoke, and deferred single-file logged-in share guardrails

### Execution groups (default S3, core, WebDAV)

- The default group (`npm run test:e2e`) is the canonical S3 gate: platform specs
  plus the S3 scratch suites (collections, retrieval, AI, trash-admin,
  `admin-config.s3`, `setup-wizard.s3`, `migration.s3`, registration-settings).
  It starts no WebDAV container.
- The core group (`npm run test:e2e:core`) runs the fast S3 subset (auth,
  core-flow, share, trash, versions, mypage-user, registration-settings). It
  includes no admin-config, migration, setup-wizard, collections, retrieval, or
  AI suite.
- The WebDAV group (`npm run test:e2e:webdav`) is the separate backend-specific
  job: `webdav-smoke-desktop` plus the WebDAV splits
  (`setup-wizard.webdav`, `migration.webdav`, `admin-config.webdav`) and
  `webdav-reconcile.spec.ts`. It uses exactly one shared bytemark.
- The default group is the required generic release gate. The core group is an
  optional fast pre-merge subset. The WebDAV job is required release coverage
  for real WebDAV-specific behavior; it is not optional just because the default
  group carries generic gate/role coverage through the S3 -> WebDAV tarpit case.
- Platform cases keep their `E2E-<DOMAIN>-NNN` IDs, and the WebDAV smoke
  deliberately reuses them. Backend-specific cases carry `E2E-S3-*` or
  `E2E-WEBDAV-*` IDs.
- No Playwright project dependencies. The worker count is supplied by CI and is
  the only concurrency throttle; scratch servers are limited by workers, not by
  an E2E slot pool. There is no per-project WebDAV container.
- The WebDAV-only case set is `E2E-WEBDAV-SETUP-001..003`,
  `E2E-WEBDAV-MIG-001..006`, `E2E-WEBDAV-ADMINCFG-001..005`, and
  `E2E-WEBDAV-RECON-001`, plus the platform cases selected by the
  `webdav-smoke-desktop` EXP/SHARE/OVERLAY/TRASH/WEBDAV-RECON grep.
- The suite/project runtime matrix and expected group counts above are the
  canonical inventory. Release runs with retries disabled, fail on flaky tests,
  and fail on any skip beyond the documented static counts.

Practical rule:

- Core-file-feature change → `npm run test:e2e:core` + `npm run test:e2e:webdav`.
- Anything touching admin/config/migration tooling, or before merging → full
  `npm run test:e2e`.
- Runs use the worker count supplied by CI (local default: Playwright's default
  pool). Order-independence is guaranteed by containment; scratch suites are
  independent siblings with project-scoped ports.

## Out of Scope for Playwright-First Coverage

Track these areas in lower-level tests even if they appear in the inventory above as `non-e2e`:

- full ACL allow/deny matrix
- login rate-limiting headers and counters
- access-token refresh retry semantics
- upload `overwrite` and `skip` branch matrix
- batch worker partial-success internals
- ZIP progress response details and skip summaries
- video preview ticket expiry behavior
- thumbnail token/signing behavior
- ACL inheritance and non-inheritance matrices beyond representative visible denial or capability smoke
- recent-files API synchronization details
- low-level drag gesture/cursor permutations beyond representative denied/no-op smoke coverage
- maintenance and cleanup endpoint result shapes beyond user-facing smoke coverage

## Known Planning Notes

- Share-link expiry semantics have drifted across docs in the past. Plan browser assertions around the visible expired/not-found UI state rather than baking in an inconsistent intermediate assumption.
- Some permission-management behaviors are better defined by implementation and route specs than by older feature prose. Where those drift, use the current route behavior for test planning and update docs alongside implementation work.
- The first implementation wave should prefer deterministic dialogs and navigation outcomes over timing-sensitive gestures.

## Maintenance Rules

- Update this document whenever product behavior adds, removes, or re-scopes a browser-visible flow.
- When adding a new flow, assign a stable `ID`, `Priority`, `Recommended layer`, and `Planned spec file`.
- Never reuse a retired ID. Backend-specific cases use the qualified `E2E-S3-<DOMAIN>-NNN` / `E2E-WEBDAV-<DOMAIN>-NNN` form, and every split is recorded in "ID Migration (S3-First Restructure)".
- If a planned flow is intentionally postponed, move it to `deferred` and record the reason in `Notes`.
- Do not use this document as a duplicate feature spec. Keep detailed behavior in feature/spec docs and keep this file focused on planning and coverage ownership.
- When a new feature introduces selector policy or platform-specific interaction rules that are meaningful at the feature boundary, add those rules to the owning `docs/features/*.md` file and keep this document as the canonical inventory/ownership source.
