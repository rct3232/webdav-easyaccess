## 1. Overview

| Item               | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Role               | The `__collections__` surface: **list mode** (grid-parity collection cards with 2×2 recent-member previews, similar-cluster headers, merge-card slot — the sort control lives in the shared toolbar) and **member mode** (an opened collection's stored ∪ derived − exclusions listing with digest + publish-pending banners). ## 2. Implementation Spec

### 2.1 File Path

- **Source:** `client/src/components/file-manager/CollectionsListView.js` (+ `CollectionCardItem.js` — the card composing `CardTile` + the 2×2 preview)
- **Test file:** `client/src/components/file-manager/__tests__/CollectionsListView.test.js`

### 2.2 Routes & Modes

- `/files/__collections__` — list mode (`include=mine,shared`).
- `/files/__collections__/collection/:id` — member mode (`GET /:id/items` **full fetch** —
  server ships the complete set in activity-score order). The host sorts the FULL row set
  CLIENT-SIDE by the persisted per-surface `collectionMemberSortMode` (default `date_desc` =
  newest-added first) BEFORE the `useInfiniteScroll` 50+50 slice — file-surface sort parity
  (`FileManagerControls.md` §2.6, §2.5 rules below). Server order remains the TIE-BREAK
  (stable sort).
- `/files/__collections__/__archive__` — list mode, `include=mine,archived`, permanent-delete affordances enabled.
- `/files/__collections__/liked` — the Likes surface: the static child row of
  the Collections sidebar section. It is a **member-parity consumer**, NOT a new mode value: the shell
  feeds `mode='members'` with rows from `GET /api/file-likes/items` through the same `toMemberRow`
  adapter and the same renderer delegation, and OMITS `digest`/`publishPendingCount`/`onPublishBatch`
  (zero banners — there is no membership or publish state on this surface) and the bulk cluster
  seams (`onBulkMemberExclude`/`onBulkAddToCollection` ⇒ toolbar renders no membership bulk buttons).
  View mode persists under its OWN per-surface key `likedViewMode` (default grid, independent of
  `collectionMemberViewMode` and file `viewMode` — `useExplorerSession.md` §2.3). The sort button
  renders here too — the liked surface shares the members surface's
  `collectionMemberSortMode` state and the same client-side sort (rows carry `created_at` = the
  NODE creation time — `fileLikes.md` §2.4.2; the "date" sort on this surface sorts by
  that stamp). The row menu is
  `MemberRowControls` with `collection:null` (no Exclude/publish; Download/Reveal/Properties/like
  toggle — `MemberRowControls.md` §2.3).

### 2.4 List Mode

- **Card = grid-parity tile:** each card is a `CollectionCardItem`
  (`client/src/components/file-manager/CollectionCardItem.js`) composed on the shared `CardTile`
  inside the shared `ResponsiveCardGrid` container (`FileGrid.md` §2.6 columns — files and
  collection cards share the responsive surface; cluster headers/merge slot are full-span children).
- **Media area = 2×2 preview:** up to 4 members from the row's `preview_items`
  (newest-added first, server-sliced). NO filename labels. Each cell carries
  `data-file-node-id` + `data-testid="collection-preview-<node_id>"` and shows the file icon
  immediately (`getFileIcon` from `{type, mime, name}`), swapping to a thumbnail `CardMedia`
  once `previewThumbnails` (Map, keyed by node id) gains that id via the batch mechanism
  (§2.3 `onPreviewThumbnailsLoaded`). A collection with no previewable members renders the sidebar collections
  glyph (`Collections as CollectionsIcon`, `fontSize="large"`, `color="action"`,
  centered in the media area, `data-testid="collection-card-fallback"`) — not a
  file-tree folder icon.
- **Footer area:** collection name ONLY (archive membership is view-scoped — no member-count
  line, no `status=archived` chip). The card menu trigger is the tile
  More action (`data-testid="card-menu-button-<id>"`), hidden while `selectionMode`
  (files parity).
- **Media badges:** corner overlays on the tile media area (shared `CardTile`
  `cornerBadges` slot, top-left; the right side hosts the More action), each a 16px icon in
  a translucent circular container:
  - received/shared (`granted_role != null`) → generic `Share` glyph (`ShareIcon`),
    tooltip reusing `nav.collectionsSharedChip`, testid `card-shared-chip-<id>`;
  - auto-pin (`pinned_by='auto'`) → composite `PushPin` + small `AutoAwesome` overlay
    (same idiom as the member publish-pending badge), rendered as a REAL BUTTON — click
    dispatches the existing `onCardAction('unpin', collection)`; aria-label/tooltip reuse
    `fileManager.collectionsAutoPin`; testid `card-autopin-chip-<id>` (the inner unpin
    CTA testid `card-autopin-unpin-<id>` on the button);
  - user pin (`pinned===true && pinned_by='user'`) → plain `PushPinIcon` badge, also a
    REAL BUTTON dispatching unpin; tooltip `fileManager.collectionsUserPin`
    ("Pinned"/"고정됨"); testid `card-userpin-chip-<id>`.
- **Click semantics = file parity:** the card container keeps
  `data-file-path="/__collections__/collection/<id>"` (the synthetic selection key for
  `getEntryKey` — numeric file node ids can never collide; also the empty-space deselect
  guard). Desktop: first click → `onCardClick(collection, event)` → shell enters selection mode
  with single-select (ctrl toggles); a second click on the SAME card within 350ms (same window
  as `useExplorerInteraction.js` desktop double-click) → open (dispatches the internal `open`
  action → `/files/__collections__/collection/:id`). Mobile: tap → open (files parity),
  long-press → `onCardLongPressSelect(collection)` starts selection. Selected cards render the
  `CardTile` selected background — the exact `FileGridItem` selected state.
- **Bulk confirm hosting:** the toolbar bulk cluster (`FileManagerControls.md` §2.6) dispatches
  through the shell; archive/permanent-delete confirms are hosted IN this view from the
  `bulkConfirm` state — bulk archive = ONE confirm; bulk permanent delete = the trash-parity
  two-step, ONE dialog for the whole batch listing the affected collection names.
- **Sort `similar`:** server pre-groups rows (`cluster_index: 0|1|…`); view renders cluster GROUP HEADERS (unlabeled visual groups), not one path order. Other sorts render a flat list. The `sort` value arrives as a render input only — the list view renders NO sort control (the toolbar's collections surface owns the menu, `FileManagerControls.md` §2.6).
- **Pseudo-tiles:** the collections GRID hosts two navigation
  tiles rendered as regular `ResponsiveCardGrid` cells on the `CardTile` shell (large centered
  icon in the media area, label in the footer — NO selection, NO cluster/menu involvement, never
  in `collections` data):
  - active list (`include !== 'mine,archived'`): FIRST cell = Likes tile (`Favorite` icon
    `color="like"`, label `nav.collectionsLiked`, testid `collection-tile-liked`, click →
    dispatch `onPseudoTileNavigate('/__collections__/liked')`); LAST cell = Archive tile
    (`Archive` icon, label `nav.collectionsArchive`, testid `collection-tile-archive`, click →
    `onPseudoTileNavigate('/__collections__/__archive__')` — routes per
    `useFileManager.js` `urlView` parsing: `/files/__collections__/liked`,
    `/files/__collections__/__archive__`).
  - ARCHIVE view (`include === 'mine,archived'`): NO pseudo-tiles at all — neither the Likes
    nor the Archive tile renders; the archive surface is the terminal view of the pair (the
    sidebar Likes/Archive nodes are the navigation destinations).
  - LIKED surface: NO tiles (member mode never renders list chrome).
  - Tiles are EXCLUDED from the `collections.length === 0` empty-state gate: an empty section
    still shows the tiles (plus the localized empty copy) — the destinations must stay reachable.
- **Card context menu by origin** — no `open` entry (opening is the double-click/tap):
  own (`user|system` rows): Rename (→ server sets `name_locked`) / pin·unpin / archive (ONE
  confirm) / Sharing (opens CollectionPropertiesDialog Sharing tab) / Delete (visible ONLY in
  `__archive__`, second-step confirm, trash-parity, report-only toast). Viewer-received rows
  (`granted_role != null`): `Revoke permission` ONLY (action `revoke-permission` — dispatched
  to the host, which runs `DELETE /:id/grants/me`; INSTANT, no confirm dialog), NO mutations.
  Rows render straight from fetch state (no view-local
  recipient-hide): the revoked row disappears on the next list read.
- **Archive view own rows** (`status=archived`, `__archive__` view): the menu renders **Restore
  in place of Archive** — Rename / pin·unpin / Restore / Sharing / Delete (restore/permanent-delete
  affordances per §2.2 and `useFolderTreeController.md` §3).
- **Menu icons:** EVERY card-menu `MenuItem` renders a `ListItemIcon`
  (files-menu parity):
  rename `Edit` · pin/unpin `PushPin` (kept) · archive `Archive` · restore `Unarchive` ·
  sharing `Share` · delete-permanent `DeleteForever` · revoke-permission `ExitToApp`
  (all from `@mui/icons-material`, same alias idiom as `FileContextMenu.js`/
  `FileManagerControls.js`).

### 2.5 Member Mode — shared-renderer rows + top-of-list banners

Member rows render through the SAME shared `FileList`/`FileGrid`/`FileDetail` renderers as files (list/grid/detail), driven by the per-surface `memberViewMode` (default **grid**, `collectionMemberViewMode` localStorage key — `useExplorerSession.md` §2.3). The member adapter (`useFileManager.md` toMemberRow) normalizes rows to file shape so the shared slots apply: the revoked placeholder is the row NAME (`fileManager.collectionsUnavailable` label substituted for the null name); the `shared_excluded` and awaiting-publish member-state BADGES render through the shared `MemberStateBadges` component in ALL three renderers (`MemberStateBadges.md`), and revoked rows render NEITHER badge; drag/drop is disabled via `hasWritePermission:false`; and the row menu is dispatched (not hosted) through `onMemberAction('menu', row, anchorEl)`. THIS view is the CHROME HOST: digest banner and publish-pending banner render around the delegated renderer; `mode==='list'` collection cards are unchanged. Member/liked rows arrive complete in one response — this host applies the shared `useInfiniteScroll` (50+50) slice + sentinel (no load-more button).

- **Digest banner:** renders ONLY when at least one delta is non-zero —
  `(digest?.added_since ?? 0) > 0 || (digest?.removed_since ?? 0) > 0` (an all-zero `since`
  digest is noise — the banner must not mount). One line
  `+N / -M / 1 merge · expand` from `GET /:id/items?since=`; `since` = the client-held
  per-collection visit stamp (localStorage `collections.digestVisits`, written on each open)
  used ONLY to request the `digest` delta counts — the server stamps its own read cursor on the
  items read and owns the sidebar `new` dot. Expanded digest renders `digest.entries` when the server exposes them; the shipped `GET /:id/items` digest is counts-only (`routes/collections.md` §GET /:id/items) — per-entry `why is this here` rows + undo links require that payload extension (surface otherwise inert).
- **Member sort:** before the
  50+50 slice, the FULL row set sorts client-side by `memberSortMode` (shared by the members
  AND liked surfaces — one persisted state):
  - `name_asc`/`name_desc` — mirror `sortFiles` semantics (`fileUtils.js`): lowercase
    `(basename || name)` `localeCompare`, directories partitioned ahead of files;
  - `date_asc`/`date_desc` — key = row `created_at`, the MEMBERSHIP-ADDED date (wire
    `serializeItem.created_at` passed through by the adapter — `useFileManager.md`; on the liked
    surface the same field carries the NODE creation time, `fileLikes.md` §2.4.2);
  - rows LACKING `created_at` (revoked members arrive `created_at: null`) PIN to the END in BOTH
    date directions;
  - the sort is STABLE — equal keys keep the server (activity/node_id) order;
  - `memberSortMode` absent ⇒ no re-sort (as-is rendering; keeps non-bindable callers intact).
- **Publish-pending banner:** owner sees `N awaiting publish` (`publish_pending_count`) with the batch `Publish all` action (→ `onPublishBatch` → `PUT /:id/items/publish`); only when the collection is live-shared and `publish_mode != auto`. Hidden for grantees (field absent server-side).
- **Row delegation contracts:**
  - `memberViewMode` (`'list' | 'grid' | 'detail'`) selects the renderer; mobile detail force-to-list applies to the member key too (`useExplorerSession.md`).
  - Single click = select through the SHARED machinery (rows carry real `nodeId`s): `onMemberRowClick` is the shell's `handleFileClick`, `onMemberRowCheck` is `handleFileCheck`, `selectedFiles` keys are numeric node ids. Double click = PREVIEW like files (the `handleFileClickInternal` file branch — member rows carry `nodeId` + `name`; the preview dialog loads by the nodeId metadata/blob endpoints, `path:''` is never used). Mobile tap = open (files parity).
  - More button AND right-click route to the shell's single `MemberRowControls` instance via `onMemberAction('menu', row, anchorEl)` (`anchorEl` = the clicked trigger / row element); `FileContextMenu`/`FileActionSheet` must NEVER open for member rows (E2E invariant: no `file-action-*` testids in member menus).
  - Testid preservation through the shared renderer: the adapter carries `rowTestId: member-row-<nodeId>` and `moreButtonTestId: 'member-menu-button'` as optional file-shape fields (`FileList`/`FileGrid`/`FileDetail` render them when present, files are unaffected). The badges keep `member-excluded-badge-<nodeId>` / `member-publish-pending-badge-<nodeId>` in EVERY member view — list overlay, grid corner (the `CardTile.cornerBadges` slot), detail inline (`MemberStateBadges.md` §2.4).
  - Revoked rows (`state:'revoked'`): gray placeholder WITHOUT real filename/thumbnail — `getFileItemState` disables them (`fileViewUtils.md` member rule), the adapter's null `mime`/name keeps `isImageOrVideoFile` false so `useThumbnailLazyLoad` never requests a thumbnail, and the row menu renders nothing but dismiss (`MemberRowControls.md`).
  - Thumbnail merge is member-local: `onMemberThumbnailsLoaded` merges into the `collectionMembers` rows (never the session file list). On the liked surface the same prop merges into the `likedItems` rows (shell-side; the view stays agnostic).
- Member rows carry icon/name/date chips from enrichment (`search.md` reuse); row states: `state:'revoked'` ⇒ gray placeholder (NO badges); `shared_excluded:true` ⇒ `Not owner's file — not shared` BADGE (tooltip `fileManager.memberNotShared`, `MemberStateBadges.md`) in all three views (owner view only — grantees never receive foreign rows server-side); trashed-by-owner ⇒ absent (server hides). Size is NEVER rendered for member rows (the wire carries no size — adapter omits the field, `FileListItem` suppresses the slot, see `useFileManager.md`).
- Initial `seed`/`search` members are already `published:true` (the create-time batch publish approval covers them) — never park in the banner retroactively.

### 2.8 Verification Scenarios

- [ ] View renders no sort control (menu dispatch is covered in `FileManagerControls.md` §2.7); `sort='similar'` renders cluster headers per `cluster_index` runs, other sorts a flat list.
- [ ] Empty suggestions ⇒ no merge-card DOM node (zero footprint).
- [ ] Banner order: merge card (list) / digest + publish-pending (members); both co-render in member mode.
- [ ] Archive-mode cards expose Delete; live cards do NOT (2-step lifecycle enforced in UI).
- [ ] Card menu has NO `open` entry: own-active = rename/pin/archive/sharing, own-archived adds restore+delete, viewer = `revoke-permission` only (instant, no confirm, no view-local hide — the card vanishes only when the next fetch omits it).
- [ ] Click parity: `onCardClick(collection, event)` on every card click (selection/open resolution is the shell's); mobile long-press dispatches `onCardLongPressSelect(collection)`; More action hidden while `selectionMode`; selected card renders the shared tile selected background.
- [ ] Card footer shows the name ONLY (no item-count caption, no `archived` chip);
      received cards overlay the `card-shared-chip-<id>` generic `Share` glyph badge and

### 2.9 Edge Cases

- Single page (one fetch): `node_id` de-dup is a server-side view-resolution property (`stored ∪ derived` by node); display slicing (head-first, stable) never re-orders rendered rows, and the §2.5 client sort runs on the full set before the slice.
- Name collision rename: server suffixes; refresh shows final name.
- Operator rule (admin is a pure operator): the surface is user-only via the guards (FolderTree mount gate + `useFileManager` urlView guard resolve admin deep links to home) — hidden / never rendered for admin; NO redundant admin checks inside the component (avoid-scatter rule).
