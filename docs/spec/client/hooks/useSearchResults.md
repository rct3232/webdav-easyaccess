# useSearchResults Spec

## 1. Overview

| Item                     | Description                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Role                     | Search **results-mode** controller: mode machine (`browse` / `pending` / `results`), the committed refinement chain with per-step snapshots, the three result zones (current-folder matches, server name matches, semantic), live-filter promotion semantics, metadata enrichment of server rows, entry-click recording, the save-to-collection save flow, and recent-query persistence. |
| Used by components/pages | `FileManager` page shell (owns the mounted surfaces); `FloatingSearchBar` (submit/clear intents), `SearchQueryChipBar` (chip strip + revert/exit), `FileManagerView` (accordion zones), `AddToCollectionMenu` (full-snapshot target)                                                                                                                                                     |
| Does not own             | Browse-mode typing filter and highlight attachment (`useExplorerSession`), row rendering (`FileList`/`FileGrid`/`FileDetail` per `FileManagerView.md`), collection-write IO (`useCollections`/gateway), chip visuals (`SearchQueryChipBar`)                                                                                                                                              |

### 2.3 State Machine, Chain, and Return Value

**Modes:** `browse` (typing = current-folder hiding filter, owned by `useExplorerSession`) → focusing the bar arms search → Enter / 56px-button submit → `pending` → response → `results`. Exiting results mode returns to `browse`: breadcrumb + FAB restored and the shared input field is RESET (empty, no browse filter). A successful commit hands the term to the chip strip and clears the shared input (`onCommit`). `pending` holds for at least one full orbit cycle (`SEARCH_ORBIT_CYCLE_MS`, `constants/fileManager.js`) after the response lands — the results commit cannot arrive before the glyph animation completes a cycle. A late commit invalidated by an exit during that window (sequence counter) is discarded.

**Exit triggers (all route through `exitResults`):** the single-chip `Exit` (`SearchQueryChipBar.md`), the `FloatingSearchBar` ✕ press while in results mode, opening a DIRECTORY result row (navigate + exit — §2.3 row clicks), and folder navigation from the sidebar/tree/breadcrumb while results mode is active (the shell calls `exitResults` on the navigation path; the sessionStorage recent-query list survives). Escape key: no behavior.

**Chain model.** A search session is a chain of committed steps:

```
ChainStep = { term, op, snapshot: { zoneAIds: Set<nodeId>, zoneBRows: [], zoneCRows: [], semanticAvailable, resultRef, predicates: [] }, inputTextAtCommit }
```

- `submitSearch(query)` from `browse` starts a NEW chain `[term]` with a fresh snapshot (the previous chain resets).
- `submitSearch(term)` from `results` appends a chain step: `POST /api/search { query: term }` is sent and the snapshot is derived by the refiner (§2.3 chain seam) from the PREVIOUS snapshot + the response.
- The name-chain op is `intersect-name`: step 1 takes the response's `name_matches` as `zoneBRows`; step k>1 sets `zoneBRows_k = ids(zoneBRows_{k-1}) ∩ name_matches(t_k)` rows. `zoneAIds_k` is recomputed client-side at every step: current-folder rows whose name contains ALL committed terms (case-insensitive substring).
- `zoneCRows` carries the snapshot's semantic rows — exactly the response's `semantic` section (server score order as delivered; entries already in `name_matches` were removed server-side). A response that omits `semantic` (the `semantic_available:false` degrade — `routes/search.md` §2.4) yields an empty Zone C snapshot; an honestly empty leg (`semantic: []` present, `semantic_available:true`) also yields zero rows while `semanticAvailable` stays `true`.
- `semanticAvailable` of each response is stored per step (`response.semantic_available === true`) — the §2.6 save-gate input for the chip bar's save affordance.
- `resultRef` of each response is stored opaquely per step (the client never parses it).
- `predicates` of each response is stored verbatim per step when the key is present (the
  parsed NL predicate atoms — `routes/search.md` §2.4); a response without the key yields
  `[]`. The snapshot carries FIELD/VALUE atoms only (the server never sends vectors or ids
  inside atoms) and the client never interprets them; the save-to-collection payload keeps
  sending `predicates: []` (the create-contract validation is unchanged — the snapshot
  predicate state is session state, not definition material).
- Chip UI = committed chain terms; `inputTextAtCommit` preserves the input text of that step.

**Chain-refiner seam (extension point).** All step derivation runs through ONE function inside the hook:

```
chainRefiner.applyStep(prevSnapshot, response, term) -> snapshot
```

Semantic refinement plugs in as a NEW `op` supplying its own `applyStep` — the chip strip, undo/revert, snapshot storage, and zone rendering are op-agnostic and unchanged by it. `resultRef` storage per step is the replay reservation a refining op consumes. The `intersect-name` refiner additionally stores the response's `predicates` array verbatim into each snapshot (§2.3) — data consumption through the existing seam only, no new op, no zone rendering (atoms surface at the header-tab seam reserved by the server contract, not here).

**Live filter (typing in `results` without submit).** Rows are NEVER hidden. A row whose name contains `liveText` (single-substring `includes`, case-insensitive) is promoted to the top of its zone and highlighted in the live color; committed-term ranges render in the committed color (`searchHighlight.md`).

**Zone ordering.** Session `sortMode` applies to Zone A and Zone B via `sortFiles`: with a live term the order is `[matches by sortMode] ++ [non-matches by sortMode]` within the zone; empty live text = pure `sortMode` order. Server rows date-sort on the ENRICHED `lastmod` (pre-enrichment the original order is kept). **Zone C is the exception:** its rows keep the SERVER's delivered order (score desc, then `node_id` asc — `routes/search.md` §2.4); the hook never applies `sortFiles` to it (an enrichment arrival or a `sortMode` change must never scramble the score ordering). The live-promotion split itself is zone-generic: a Zone C row whose name contains the live term is promoted to the zone top with its relative order preserved.

**Row click semantics:** FILE row → `recordEntryClick` + preview dialog while results stay mounted. DIRECTORY row → `recordEntryClick` + navigate + exit results (same path as the browse rule).

**Enrichment.** Server rows arrive without `type`/`size`/`lastmod`/`mime`/permission flags (`routes/search.md` returns name data only). The hook enriches them through the gateway metadata seam (`loadNodesMetadata`): `POST /api/files/metadata` with nodeIds chunked to ≤ 100 by the seam (the endpoint cap; the search section cap is 200), fired per chunk, merged by nodeId, missing rows tolerated. Rows render enriched progressively; the size caption stays suppressed until enriched (`FileListItem.md`, `FileGrid`/`FileDetail` row rules). The enriched row carries `hasReadPermission`/`hasWritePermission` for the read-only badge + bulk gating (`FileManager.md` §7).

**Zone thumbnails (zone-local merge).** Zone B/C rows are real `FileList`/`FileGrid` rows carrying `data-file-node-id`, so the zone surface's shared `useThumbnailLazyLoad` instance (`useThumbnailLazyLoad.md`) requests their thumbnails once enrichment supplies `mime` (or the name resolves to image/video). The batch response lands on `handleZoneThumbnailsLoaded(thumbnailMap)` — the ZONE-LOCAL merge seam (member-surface precedent `useFileManager.md`): merged `nodeId → thumbnailUrl` entries live in hook state (never the session listing) and the row adapter applies them to `zoneBRows`/`zoneCRows`, so a merged URL survives every row re-derivation (enrichment arrival, live-filter promotion, sort changes, chain steps). The map never overwrites its own entries; an enrichment-supplied `thumbnailUrl` takes precedence in the row. Zone A rows are session rows — their renderer keeps the session `handleThumbnailsLoaded` merge (`useExplorerSession.md`). Empty/non-Map payloads are ignored; `exitResults` clears the map alongside the enrichment state.

### 2.4 Dependencies

- **Must route IO through:** `explorerGateway` search seams (`runSearch`, `loadNodesMetadata`, `recordSearchClick`).
- **May use:** pure helpers only for filter/highlight math (`searchHighlight.js` — ranges are computed client-side, the server never returns markup offsets) and `sortFiles`.
- **Must not use:** `fetch` or `sessionStorage` directly (recent-query persistence goes through the browser-storage adapter seam in the gateway layer, not this hook).

### 2.5 Side Effects

- Server calls: `POST /api/search` on submit only (typing never calls the API); `POST /api/files/metadata` per enrichment chunk after a response; `POST /api/search/click` on row open; `POST /api/collections` from `saveFromResults` only (the §2.6 save boundary).
- `usage_events(search_hit)` logging is a server side effect of the search response; the client does nothing extra for it.
- Entering/exiting results mode does not touch the explorer listing state (`useFileManager` unaffected); the shared `searchQuery` text is cleared on commit and on exit (input reset), never on transitions that keep results mounted.

### 2.6 Error Handling

- `runSearch` → `null` (transport/5xx): `showError` (`serverErrors.search.fail`), stay in prior mode/chain with the previous snapshot intact.
- 400 cases are pre-guarded client-side; if still returned, map `serverErrors.search.queryRequired/queryTooLong` via the error envelope.
- `semantic_available:false` with `semantic_unavailable_reason` is a SUCCESS payload — Zone C stays empty (renders nothing); never an error toast (an absent section of a successful query is not an error).
- Enrichment chunks that fail or return rows missing a nodeId: those rows stay unenriched (size suppressed); no toast, no blocking of the other rows.

### 2.7 Verification Scenarios

- [ ] Typing never calls `runSearch`; Enter/button submit does — from `browse` it starts chain `[term]`, from `results` it appends a step.
- [ ] Step 2+ intersect: `zoneBRows` shrink to the intersection of the previous ids and the new response's name matches; ZERO client re-fetch of earlier terms.
- [ ] `undoToStep(i)` restores step `i`'s snapshot and discards later steps with NO server call; `zoneAIds`/`zoneBRows`/`zoneCounts` all come back from the snapshot.
- [ ] Live typing hides NO row; matched rows promote within each zone and carry live-highlight ranges; committed-term rows keep committed-color ranges.
- [ ] `zoneCounts` are snapshot counts and never change while a live term is typed/cleared.
- [ ] `libraryAddTarget` = union of `zoneAIds` and the FULL `zoneBRows` + `zoneCRows` id sets (deduped-out display rows included), unchanged by paging or live filter.
- [ ] Enrichment batches rows into chunks of ≤ 100 through the gateway seam; rows merge by nodeId; a missing row leaves the row unenriched.
- [ ] `handleZoneThumbnailsLoaded` with a `Map(nodeId → thumbnailUrl)` attaches the URL to the matching Zone B/C rows; merged URLs survive re-derivation (live filter, later enrichment, chain steps); the map never overwrites its own entries and an enrichment-supplied `thumbnailUrl` wins in the row; non-Map/empty payloads are ignored; Zone A rows keep session-merge thumbnails; `exitResults` clears the map.
- [ ] Every exit trigger calls `exitResults` and returns `mode === 'browse'`; the shared input field is reset by the shell exit seam.
- [ ] Folder navigation while in `results` exits results mode; the recent-query sessionStorage list survives; the input field is empty afterwards.
- [ ] A fast response still holds `pending` for at least `minPendingMs` before committing; `exitResults` during that window discards the late commit (mode stays `browse`, chain empty).
- [ ] `recordEntryClick` routes through the gateway seam exactly once per call and absorbs failures silently (no toast, no throw).
- [ ] Absorbed search failure produces `showError` and leaves the previous chain/snapshot intact.
- [ ] Re-submitted identical query: no duplicate recent entry (normalized-query dedup).
- [ ] Zone C rows render in the delivered score order under ANY session `sortMode` (no client re-sort); a live term promotes matching Zone C rows without changing their relative order.
- [ ] A node displayed in Zone A is deduped out of Zone C display while `zoneCounts.zoneC` keeps the full snapshot count.
- [ ] `semanticAvailable` mirrors the response flag per step: `true` on an available (even honestly empty) leg, `false` when `semantic` is omitted; a refinement step replaces the Zone C snapshot with the fresh response's section.
- [ ] A response carrying `predicates` stores the atom array verbatim in that step's snapshot (`snapshot.predicates`); a response without the key stores `[]`; `saveFromResults` still posts `predicates: []` regardless of snapshot atoms; `undoToStep` restores the per-step atom arrays with NO server call; `exitResults` clears them with the chain.
- [ ] `saveFromResults` posts `{ name, semantic: { resultRef, predicates: [], nodeIds } }` through the gateway `createCollection` seam exactly once for an available, non-empty Zone C snapshot (the reconciled wire shape of the `POST /api/collections` `{ name, semantic }` dispatch arm); it bails with `null` and ZERO calls when the section is unavailable, empty, or `resultRef` is missing; an absorbed create failure resolves `null` and surfaces no undo affordance. The confirm dialog is host-owned and precedes every create call (no create fires from the chip click alone).

### 2.8 Edge Cases

- Dedup for display: a node in BOTH Zone A and Zone B (or Zone A and Zone C) renders only in Zone A (server sections are already deduped by `routes/search.md`; the client dedups Zone A against Zone B/C display, never the snapshot).
- `counts.name_truncated:true` / `semantic_capped_segments:true`: render as-is, no client warnings (display honesty).
- Chain after `intersect-name` empties `zoneBRows`: the chain still commits the step (honest empty Zone B + Zone A recomputed); empty overall result renders the no-results line (`fileManager.searchNoResults`) without zone headers.
- A refining `op` (new `chainRefiner` implementation) receives the same inputs; nothing in the hook reads `op` outside the refiner dispatch.
- Trashed nodes never appear (server contract — the visible-row query hides `deleted_at` rows).
