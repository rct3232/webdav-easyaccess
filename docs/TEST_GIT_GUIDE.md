### 2. Test Configuration

```
✓ jest.config.js (server only; client uses Jest config in package.json)
✓ test-setup.js (server)
✓ server/test-utils.js
✓ setupTests.js (client)
✓ playwright.config.ts
✓ e2e/global-setup.ts
✓ e2e/global-teardown.ts
```

**Reason**: Needed to keep the test environment consistent.

### 3. Test Utilities and Mocks

```
✓ client/src/mocks/handlers.js
✓ server/test-utils.js
✓ e2e/helpers/**/*.ts
✓ e2e/fixtures/**/*
```

**Reason**: Common utilities needed for writing tests.

> Note: The MSW server (`setupServer`) is created in `client/src/setupTests.js` (see Test Configuration above); there is no separate `client/src/mocks/server.js`.

### 4. Jest Node Runtime Flag

```
✓ server/package.json test scripts carry
  NODE_OPTIONS='--max-old-space-size=8192 --experimental-vm-modules'
```

**Reason**: The jest process must allow dynamic `import()` of ESM-only packages —
`pdfjs-dist` (legacy build, ESM-only) is loaded lazily by the server text extractor
(`server/domains/ai/extractors/documentText.js`) and its tests. Without the flag jest
fails with "A dynamic import callback was invoked without --experimental-vm-modules".
The flag is additive for CommonJS suites and must not be removed from the scripts.

### 4. Test Documentation

```
✓ TEST_SUMMARY.md (client/server)
✓ docs/TEST_GIT_GUIDE.md
✓ docs/E2E_COVERAGE_PLAN.md
✓ README.md (testing section)
```

**Reason**: Documents test structure and how to run tests.

### 5. Package Configuration

```
✓ package.json (with test scripts)
✓ package-lock.json
```

**Reason**: Dependency information needed to run tests.

## What to Exclude from Git (.gitignore)

### 1. Coverage Reports

```
✗ coverage/
✗ .nyc_output/
✗ *.lcov
```

**Reason**:

- Generated differently per run
- Large and frequently changing
- Can be generated by CI/CD

### 2. Jest Cache

```
✗ .jest-cache/
```

**Reason**: Temporary files for performance; auto-generated per environment.

### 3. Test Result Files (Optional)

```
✗ test-results/
✗ *.xml
✗ junit.xml
```

**Reason**: Report files produced by CI/CD.

## Playwright E2E Prerequisites

Before running `npm run test:e2e`, make sure the browser-level environment is ready:

```bash
# 1. Install Playwright browsers when needed
npm run test:e2e:install

# 2. Run the full E2E suite
# This command automatically handles:
# - Bringing the Docker-backed WebDAV/PostgreSQL/MinIO services up and waiting
#   until they are healthy (provisioned by the `e2e:server` webServer command
#   via `scripts/e2e-wait-healthy.mjs` before the app server boots — no manual
#   `dev:webdav:start` prerequisite)
# - Resetting the data state without restarting services: TRUNCATE all app
#   tables (preserving `_schema_migrations`) and re-seed admin + base users
#   with home `file_nodes` roots; empty the MinIO bucket (s3 mode)
# - Starting the E2E API/server (port-band API slot, default 5002)
# - Starting the E2E client (port-band client slot, default 3000)
# - Executing the Playwright tests
npm run test:e2e

# Run a specific backend mode (default is s3)
#   s3     → FULL UI matrix: essentials + mypage-admin + hermetic suites
#            (.env.e2e). The single canonical UI run (Option A 2026-09-07).
#   webdav → thin backend-wiring smoke (chromium desktop; .env.e2e.webdav).
#            The full webdav UI duplicate is retired — the webdav server mode
#            is covered by the hermetic suites in the s3 run plus this smoke.
npm run test:e2e:s3
npm run test:e2e:webdav

# Run the standalone E2E server in a given mode (picks the matching env file;
# also brings the Docker stack up and waits for healthy containers first)
E2E_BACKEND_MODE=webdav npm run e2e:server

# Essential-only run (core file-exploration flows; skips mypage-admin and the
# hermetic setup-wizard/admin-config/migration suites). s3 only.
npm run test:e2e:core:s3

# Webdav-mode smoke also via the core alias (identical project set).
npm run test:e2e:core:webdav

# Run only the setup-wizard project (hermetic scratch instance on :5003). The
# setup-wizard-desktop/-mobile projects are defined ONLY when E2E_BACKEND_MODE=s3
# (full-mode matrix): playwright.config.ts builds the hermetic projects in its
# non-webdav branch. Under E2E_BACKEND_MODE=webdav the only projects are
# webdav-smoke-setup + webdav-smoke-desktop, which grep the EXP/SHARE/OVERLAY
# nets and never include the wizard suite.
E2E_BACKEND_MODE=s3 npx playwright test --project=setup-wizard-desktop
E2E_BACKEND_MODE=s3 npx playwright test --project=setup-wizard-mobile
```

Required assumptions:

- Docker must be installed and running on the host machine.
- `playwright.config.ts` is configured with `webServer` to manage the client and server lifecycle automatically.
- The E2E Docker stack (`docker-compose.e2e.yml`: WebDAV, PostgreSQL, MinIO) is provisioned by the `e2e:server` webServer command before the app server boots: `scripts/e2e-wait-healthy.mjs` runs an idempotent `docker compose up -d` and polls `docker compose ps` until the mode's required compose SERVICES report `healthy` (webdav-test + postgresql-e2e always; minio-e2e in s3 mode only). The stack defines no `container_name:` entries — container names stay project-scoped (compose derives the project from the checkout directory), and every helper (`e2e-wait-healthy.mjs`, `e2e/global-setup.ts`, `e2e/helpers/setupScratch.ts`, `e2e/webdav-reconcile.spec.ts`) addresses containers via `docker compose … <service>` instead of a global container name, so parallel E2E runs from multiple git worktrees never collide on shared container names. If two checkouts share a directory basename, set `COMPOSE_PROJECT_NAME` to disambiguate them. `e2e/global-setup.ts` re-runs the same helper idempotently as belt-and-braces (it never tears the stack down), restarts the WebDAV container once in BOTH modes (after wiping its `data/webdav` bind-mount, so no mid-run lazy restart is needed by the hermetic suites), then resets the data state: it TRUNCATEs all app tables (preserving `_schema_migrations`) and re-seeds the default admin and base users with home `file_nodes` roots via `e2e/global-setup.seed-db.cjs`, ensures the MinIO platform and migration buckets in both modes, and empties the platform bucket in s3 mode. `e2e/global-teardown.ts` empties the S3 bucket (s3 mode) and stops the services (`down -v` — project-scoped, it only ever affects the current checkout's stack).
- The root Playwright config builds the projects from the active backend mode (Option A): `E2E_BACKEND_MODE=s3` defines the desktop/mobile UI matrix (`s3-desktop-setup`/`s3-desktop`, `s3-mobile-setup`/`s3-mobile`) plus the hermetic additive projects (setup-wizard/admin-config/migration, which boot their own webdav-mode scratch servers); `E2E_BACKEND_MODE=webdav` defines a thin smoke pair (`webdav-smoke-setup`/`webdav-smoke-desktop`) that greps the backend-wiring nets out of `core-flow.shared`/`share-public`/`share-internal`. Only the projects for the active mode are defined, so `npm run test:e2e:s3` runs the full s3 matrix and `npm run test:e2e:webdav` runs only the smoke (check with `E2E_BACKEND_MODE=s3 npx playwright test --list`).
- The backend mode is selected via `E2E_BACKEND_MODE` (`s3` default, `webdav` legacy). The `e2e:server` script chains `scripts/e2e-wait-healthy.mjs` (port-band provisioning + compose up + health wait), then boots the server with `DOTENV_CONFIG_PATH=../data/e2e-runtime.env` — a file GENERATED from the mode's base env (`../.env.e2e` for s3, `../.env.e2e.webdav` for webdav) with this checkout's band ports written into `PORT`, `CORS_ORIGINS`, `WEBDAV_URL`, `WEBDAV_UPSTREAM_URL`, `S3_ENDPOINT` and `WEA_DB_PORT` (git-ignored; never edit it by hand). Default host-exposed ports are MinIO 9010/9011, PostgreSQL 5433 and WebDAV 8090 — at band offset 0 these are the historical fixed numbers, so single-checkout workflows are unchanged.
- Specs branch on the project name platform suffix (`testInfo.project.name.endsWith('-desktop')` / `endsWith('-mobile')`), so the platform checks keep working under the mode-prefixed project names.
- The hermetic additive suites (setup-wizard / admin-config / migration / trash-admin / collections / retrieval / ai) are isolated per suite and run as independent siblings (Option A): setup-wizard boots its scratch server on the `:5003` slot, admin-config on `:5010`, migration on `:5011`, trash-admin on `:5012`, collections-lifecycle on `:5013` (ONE dual-platform file: the desktop and mobile projects share the slot via the dependency chain — the former standalone mobile twin on `:5014` is retired), retrieval (search results mode, `e2e/retrieval.spec.ts`) on `:5015` and the semantic-search suite (`e2e/ai.spec.ts`) on `:5016` (their playwright.config baseURLs mirror this; all slots shift together with the checkout's port band — see "Parallel E2E runs" below); each has its own env file/sqlite/PG namespace and migration uses a dedicated MinIO bucket. Each spawns its own scratch server and supervises its own process lifecycle (restart is the behavior under test for the wizard; the destructive-case policy requires own-server isolation for trash-admin/collections). They do not use the shared `:5002` server or `:3000` client. A suite's mobile variant depends on its desktop variant so one suite never overlaps itself on the same port. `collections.spec.ts` boots ONE scratch server for the whole file (restart is not under test; the file is serial and case-contained) and runs under BOTH the collections-desktop and collections-mobile projects (dual-platform format — the mobile variant chains after the desktop one on the shared slot; the mobile-only interplay cases skip on desktop with reason-carrying skips).

### Parallel E2E runs (multiple git worktrees / checkouts)

The E2E environment avoids ALL globally-shared resources so two checkouts can run
their suites concurrently:

- **Container names** — `docker-compose.e2e.yml` pins no `container_name:`; names are
  project-scoped (`<project>-<service>-<n>`, project = checkout directory name). All
  helpers address containers through `docker compose -f docker-compose.e2e.yml
<cmd> <service>`. If two checkouts share a directory basename, export a distinct
  `COMPOSE_PROJECT_NAME` per checkout.
- **Host ports** — `scripts/lib/e2e-band.cjs` allocates one PORT BAND per checkout:
  a single offset (steps of 20) applied to the whole base port set
  (`client 3000`, `api 5002`, scratch slots `5003/5010-5016`, `webdav 8090`,
  `pg 5433`, `s3 9010/9011`). Offset 0 is tried first and reproduces the fixed
  contract exactly, so a solo checkout sees no change. Allocation happens once per
  checkout and is PERSISTED in `data/e2e-runtime.json` (git-ignored) — reusing the
  same band on every later run keeps `reuseExistingServer` dev loops stable. A band
  is taken only when every port passes a real listener probe AND a global claim lock
  (`<tmpdir>/webdav-e2e-ports/band-<offset>.lock`, stale dead owners are reclaimed)
  — this closes the race between concurrent cold starts of different checkouts.
  If another live checkout later claims our persisted band (e.g. after a /tmp
  sweep), the next run reallocates transparently.
- **Consumers** — compose interpolates `${E2E_WEBDAV_PORT…}` from the env that
  `scripts/e2e-wait-healthy.mjs` exports; the API server boots on
  `data/e2e-runtime.env`; `playwright.config.ts`, the scratch suites and the
  setup/teardown helpers all resolve ports through `e2e/helpers/ports.ts`
  (per-port `E2E_*_PORT` env overrides win over the persisted band). Loading the
  Playwright config triggers band allocation, so even a bare `playwright test`
  from a second checkout moves off a busy default band automatically.

Run commands (both backends/modes unchanged otherwise):

```bash
# Checkout A (first / solo): uses offset 0 = today's fixed ports.
npm run test:e2e:s3

# Checkout B (concurrent): base ports are busy → auto-allocates offset 20.
npm run test:e2e:s3

# Deterministic pinning for orchestrated parallelism (e.g. CI fan-out):
E2E_PORT_OFFSET=40 npm run test:e2e:s3   # must be a multiple of 20

# Inspect the current checkout's band:
cat data/e2e-runtime.json

# Force re-allocation (band conflict after /tmp cleanup, stale pins):
rm data/e2e-runtime.json data/e2e-runtime.env   # lock is reclaimed automatically
```

Intentionally NOT isolated (per-run, not per-machine): Docker image pulls (daemon-side
dedup is safe), `e2e-data/`/`test-results/`/`client/build` (already per-checkout), and
Playwright browsers (shared read-only cache under `~/.cache`).

## Recommended Git Workflow

### 1. New Feature Development

```bash
# 1. Create feature branch
git checkout -b feature/new-feature

# 2. Write tests first (TDD)
# - Create and write test files

# 3. Run tests (expect failure)
cd client && npm test
cd server && npm test

# 4. Implement code

# 5. Run tests (expect success)
cd client && npm test
cd server && npm test

# 6. Check coverage
cd client && npm run test:coverage
cd server && npm run test:coverage

# 7. Commit (tests and code together)
git add .
git commit -m "feat: add new feature + tests"
```

### 2. Bug Fix

```bash
# 1. Write a test that reproduces the bug
# 2. Run tests (expect failure)
# 3. Fix the bug
# 4. Run tests (expect success)
# 5. Commit
git commit -m "fix: fix bug + regression test"
```

### 3. Refactoring

```bash
# 1. Ensure all existing tests pass
cd client && npm test && cd ../server && npm test

# 2. Refactor

# 3. Run tests again (still passing)
cd client && npm test && cd ../server && npm test

# 4. Commit
git commit -m "refactor: refactoring (tests pass)"
```

## CI/CD Integration

### GitHub Actions Example

```yaml
name: Tests

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v2

      - name: Setup Node.js
        uses: actions/setup-node@v2
        with:
          node-version: '18'

      - name: Install dependencies
        run: |
          cd client && npm ci
          cd ../server && npm ci

      - name: Run client tests
        run: cd client && npm run test:ci

      - name: Run server tests (sqlite)
        run: cd server && npm run test:ci

      # Tiered real-PostgreSQL coverage (TESTING_STRATEGY.md: functional suites run on
      # sqlite once; per-RDB adapter conformance runs against real PG).
      # The disposable `webdav_test` DB is self-provisioned by the test
      # harness when missing (see server/test-utils.js).
      - name: Run server adapter tests (postgresql)
        run: |
          docker compose -f docker-compose.e2e.yml up -d postgresql-e2e
          cd server && npm run test:ci:pg:adapters

      - name: Upload coverage
        uses: codecov/codecov-action@v2
        with:
          files: ./client/coverage/lcov.info,./server/coverage/lcov.info
```

## Coverage Goals

### Current Status

Raw test counts are intentionally **not duplicated here** (choice recorded 2026-09-09: they drift between runs; the summaries below are the single source of truth).

- **Client**: current suite/test counts, pass rate and snapshot date — see `client/TEST_SUMMARY.md` (Test Statistics).
- **Server**: current suite/test counts, pass rate and snapshot date, plus the real-PG adapter leg (`test:ci:pg:adapters`) latest recorded run — see `server/TEST_SUMMARY.md` (Test Statistics).
- Coverage figures are measured per run via `npm run test:coverage` (uploaded to Codecov in CI); the `TEST_SUMMARY.md` files document how to measure rather than freezing figures.

### Recommended Targets

- **New code**: Minimum 80% coverage
- **Refactored code**: Minimum 90% coverage
- **Core business logic**: 95%+ coverage

### Checking Coverage

```bash
# Client
cd client && npm run test:coverage

# Server
cd server && npm run test:coverage
```

### Mutation Testing (Stryker)

Coverage alone can be misleading—tests may cover code without catching real bugs. Mutation testing (Stryker) mutates your code and checks if tests fail; a high Mutation Score means your tests are effective.

```bash
# Client (uses create-react-app Jest)
cd client && npm run test:mutation

# Server (uses custom Jest)
cd server && npm run test:mutation
```

Recommendation: Prioritize improving the Mutation Score over coverage percentage. Start with small modules (e.g. `server/utils/errorHandler.js`) and expand the mutate scope gradually. See `stryker.config.json` in each package for the mutate range.

## Troubleshooting

### Q: Coverage report was added to Git

```bash
# Remove if already committed
git rm -r --cached coverage/
git commit -m "chore: remove coverage from git"

# Verify .gitignore
cat .gitignore | grep coverage
```

### Q: Tests pass locally but fail in CI

```bash
# 1. Check environment variables
# 2. Check Node version
# 3. Pin dependency versions (commit package-lock.json)
# 4. Ensure test isolation (beforeEach/afterEach)
```

### Q: E2E tests pass on first run but fail on second run

**Root cause**: The `data/webdav/` directory is a Docker bind mount (`./data/webdav:/var/lib/dav`). While `docker compose down -v` removes named Docker volumes, it does NOT clean host-path bind mounts. Stale WebDAV data from the previous run persists, causing conflicts.

**Fix**: Ensure `e2e/global-setup.ts` includes `cleanDir('data/webdav')` before the E2E services start. This is already handled in the default global-setup — if this issue occurs, verify the cleanup step is present.

### Q: Mobile Action Sheet tests are flaky (E2E-EXP-006, E2E-MOBILE-002)

**Root cause**: `openActionSheet` helper waits for `[role="dialog"]` to be visible. MUI's `SwipeableDrawer` has a CSS transition (~200ms) during which the element is in DOM but not fully visible, causing Playwright's `toBeVisible()` to fail with a race condition.

**Fix**: The `openActionSheet` helper now uses `Promise.all` to click and wait simultaneously, and targets specific action items (`[data-testid="file-action-rename"]`) instead of the generic `[role="dialog"]` locator. E2E-MOBILE-002 no longer redundantly checks `[role="dialog"]` after `openActionSheet`.

### Q: Tests are too slow

```bash
# Enable parallel execution
npm test -- --maxWorkers=4

# Run only changed tests
npm test -- --onlyChanged

# In watch mode, run only related tests
npm test
```
